Das große Bild

Das mentale Modell von Flutter

Eine Flutter-App ist ein System aus Zustand, Ereignissen und deklarativ beschriebenen Widgets. Ereignisse verändern Daten; Benachrichtigungen lösen einen neuen Build aus; Flutter gleicht die neue Beschreibung effizient mit der bestehenden Oberfläche ab.

Gedächtnis

Eine momentane, unveränderliche Beschreibung dessen, was Flutter anzeigen soll.

Prüfungsantwort: Flutter arbeitet deklarativ. Der aktuelle State wird durch build() in einen Widget-Baum übersetzt. Ändert sich State, markiert ein Mechanismus wie setState() oder notifyListeners() den betroffenen Bereich für einen erneuten Build; Flutter aktualisiert anschließend nur die nötigen Teile der gerenderten Oberfläche.

Warum ist build() Inversion of Control?

Nicht euer Code zeichnet eigenständig den Bildschirm. Flutter ruft build() dann auf, wenn es eine Beschreibung benötigt. Dasselbe gilt für initState(), Button-Callbacks und dispose(): Das Framework kontrolliert den Ablauf, eure Klassen liefern Verhalten.

Interaktive Entscheidungshilfe

Wo gehört mein State hin?

Wähle eine Situation aus. Die passende State-Strategie erscheint hier.
Wichtig: App-State ist nicht das GoF-State-Pattern

App-State sind aktuelle Daten wie Sternezahl oder Woche. Das State-Entwurfsmuster kapselt zustandsabhängiges Verhalten in austauschbaren Zustandsobjekten. Beide heißen „State“, lösen aber verschiedene Probleme.

Prüfungsantwort: State wird benötigt, weil eine interaktive Oberfläche sich über die Zeit verändert. In CampusMensa bleibt kleiner UI-State lokal in einem StatefulWidget; fachliche Daten liegen in Model/Repository und werden durch Controller geändert. Danach informiert notifyListeners() die ListenableBuilder-Views, die sich aus dem aktuellen Zustand neu aufbauen.

Stolperfalle: build() ist kein einmaliger Initialisierer

Warum wird nach await mounted geprüft?

Während die Kameraseite geöffnet ist, könnte das ursprüngliche Widget aus dem Baum entfernt werden. Dann darf sein State nicht mehr mit setState() aktualisiert werden. mounted schützt genau davor.

MVC: Rollen trennen, Datenfluss erklären

MVC überbrückt laut Skript die Lücke zwischen mentalem Modell des Menschen und digitalem Modell. Es trennt Fachlichkeit, Präsentation und die Verarbeitung von Aktionen. CampusMensa folgt einer MVC-nahen Schichtung mit zusätzlichem Repository.

Repository ist kein vierter MVC-Buchstabe, sondern kapselt die Datenquelle innerhalb der Model-/Daten-Schicht.

Model

Struktur + Fachzustand

Meal, MealPlan, MealReview, MealType sowie MealRepository. Private Felder werden über Java-ähnliche Methoden gelesen und geändert.

View

Darstellung

WeekplanPage, EssenPage, ReviewsPage, Dialoge und Widgets. Sie lesen Modeldaten und erzeugen die Präsentation.

Controller

Aktion + Koordination

MealController, WeekPlanController, ReviewController, AuthController. Sie nehmen UI-Absichten an und koordinieren Änderungen.

Pull beziehungsweise Poll

Der Controller verändert und befragt das Model und ruft anschließend Views auf. Bei zyklischem Nachfragen wird Pull zu Poll. Nachteil: Der Controller trägt viel Aktualisierungsarbeit.

Push

Das aktive Model beziehungsweise eine beobachtbare Logik signalisiert Änderungen. Beobachter reagieren, ohne dass der Controller jede View direkt kennen und aufrufen muss.

Push-artige Aktualisierung

Controller erben von ChangeNotifier. Nach einer Mutation rufen sie notifyListeners() auf. ListenableBuilder ist registrierter Beobachter und baut die betroffene View neu. Die View zieht beim Build die aktuellen Werte über Getter.

Geteilte Instanz ≠ Singleton

MyApp erzeugt einmal MealRepository() und injiziert dieselbe Referenz in drei Controller. Das garantiert innerhalb dieser Komposition eine gemeinsame Datenbasis. Die Klasse selbst verhindert aber keine zweite Instanz und ist daher formal kein Singleton.

Setter allein aktualisieren keine UI

review.setRating(2) mutiert das Model. Sichtbar wird die Änderung erst, weil der Controller anschließend notifyListeners() ausführt und die View die Getter erneut liest.

Selbsttest

Warum reicht ein Java-ähnlicher Setter nicht aus, um die Oberfläche zu aktualisieren?

Der Setter verändert nur den Wert im Modelobjekt. Flutter weiß davon noch nichts. Ein Aktualisierungssignal wie notifyListeners() oder setState() markiert den relevanten UI-Bereich für einen neuen Build. Beim Build liest die View den neuen Wert über den Getter.

  • „Widget ist eine Konfiguration“ statt „Widget ist das langlebige Objekt“.

Typische Fragen – kompakte Antworten

Was passiert, wenn CampusMensa startet?

main() initialisiert das Binding und ruft runApp() auf. Flutter erzeugt MyApp und dessen State. In initState() entstehen ein gemeinsames Repository und vier Controller. build() konfiguriert MaterialApp mit Locale, Delegates, Theme und NavigationShell. Danach baut Flutter die erste Seite und rendert den ersten Frame.

Warum braucht die App State?

Ohne State könnte sie sich keine Auswahl oder Änderung merken. Beispielsweise bestimmen _selectedIndex, _locale, Gerichte, Reviews und Wochenpläne, was angezeigt und wie reagiert wird. Lokaler State wird mit setState(), geteilter fachlicher State über Controller und notifyListeners() sichtbar gemacht.

Warum wird beim Review-Edit das Objekt verändert und nicht ersetzt?

Die Bearbeitung ruft die Setter des bereits gespeicherten MealReview auf. Dadurch bleibt die Objektidentität erhalten und andere Referenzen zeigen weiterhin auf dasselbe fachliche Objekt. notifyListeners() veranlasst die View, die neuen Werte über Getter einzulesen.

Wie hält die App MVC ein?

Models kapseln Fachwerte, Views stellen sie dar und Controller übersetzen UI-Aktionen in Änderungen. Das Repository kapselt die gemeinsame Datenhaltung. Über ChangeNotifier entsteht ein Push-Signal zur View, die anschließend Werte pull-artig über Getter liest. Deshalb ist die Architektur praktisch MVC-nah mit Observer-Anteil.

Wie funktioniert Localization?

Die aktive Locale liegt in MyApp und wird an MaterialApp übergeben. Ein Delegate lädt AppLocalizations. Widgets nutzen stabile Schlüssel, um deutsche oder englische Werte zu erhalten; intl formatiert Preise passend zur Sprache.

Lerncheck

60-Sekunden-Challenge

Erkläre den kompletten Datenfluss beim Bearbeiten eines Reviews.

Die View öffnet den Editor mit dem vorhandenen MealReview. Der Dialog initialisiert seine lokalen Formularwerte über getRating() und getMealComment(). Beim Speichern gibt er reine Formdaten zurück. Die View übergibt vorhandenes Objekt und neue Werte an ReviewController.updateReview(). Der Controller ruft setRating(), setMealComment() und optional setMealImage() auf und verändert damit dasselbe Objekt. Danach sendet notifyListeners() ein Push-Signal. Der ListenableBuilder baut die Review-Liste neu; sie liest die geänderten Werte mit den Get-Methoden. Das ist MVC-nahe Trennung mit Observer-Mechanismus.
